宝玉 @dotey
不知道你有没有用过 /retro Skill，就是在编码任务完成后，让 AI 复盘刚结束的工作，列出几条修改建议，由人决定采不采纳。 除了 /retro 这个用在写代码上的，还有一些其他类似的复盘自我进化的 skill，听起来很美好：AI 干完一个任务后，回头看自己哪里卡住了，再提议修改 Skill，下次就不用再重复同样的弯路。这样不用重新训练模型，只修改 Skill 文件。 其实我一直是抱怀疑态度的，如果没有清晰的标准还是挺难自我优化好的。完全依赖人的话也难，一方面对人的要求有点高，另一方面每次这么做一下也挺累。 有篇论文《How Do Coding-Agent Harnesses Self-Evolve? An Empirical Study of Retrospective Adaptation》，专门测试了"让 AI 编程助手干完活后自己复盘、修改工作手册"的做法。 结果是，7 次有效测试里只有 2 项改动彻底消除了想解决的问题，有的改动还让 AI 在不相关的任务上多做了检查。 论文作者是新加坡管理大学的 Christoph Treude 和德国海德堡大学的 Sebastian Baltes，论文 10 月 26 日发布在 arXiv 上。 研究方法是这样的。 作者从 SWE-bench Verified 中选了 30 个问题，这是一套从真实开源项目里收集的代码修复题目，涉及 Django、SymPy、Astropy 等 Python 项目。 前 10 个是随机抽的，后 20 个专门从之前碰到过环境问题的项目里挑，比如项目里本来就有测试失败。Claude Code 每修完一个问题就运行一次 /retro，一共得到 125 条建议。 作者挑出 24 条让 Claude Code 落实，其中 11 项能拿来测试，再加上作者自己写的 1 项对照，共 12 项。测试时，在同一个项目里找另一个确认会出现同样问题的任务，用原来的设置跑 5 次，用改过的设置再跑 5 次，比较 AI 会不会再做那个本想避免的动作。 这次研究用的是 Anthropic 的 Claude Code，背后的模型是 Opus 5.5。 主要发现有四点： 1. 大部分建议有依据。 125 条里有 101 条针对的是任务中真实发生的事。另有 19 条的理由跟这次任务里发生的事无关，其中 18 条是建议加代码格式检查。 原因之一是 /retro 的指令本身就规定，项目里没有提交前检查、也没有自动化检查流程的，算作一个"发现"。作者把其中一条"提交代码前自动跑格式检查"配置好后测试，5 次里 AI 一次都没读它，也没运行它。 2. 13 次测试里，只有 7 次在原设置下真的碰到了目标问题，结果才有参考意义。 这 7 次里，彻底消除问题的有两项。 一项是在 CLAUDE.md 里写明 SymPy 项目要用 bin/test 跑测试，并说明没有安装 pytest。改之前，5 次里 5 次都先去试 pytest 然后失败；改之后是 0 次。 另一项是给 Astropy 项目写了一份"本来就会失败的测试清单"。 以前 AI 遇到测试失败，会在没改过的原始代码上再跑一遍测试做对比，确认失败是不是自己造成的；有了清单，它直接查清单，这种对比从 5 次中的 3 次降到 0 次。 3. 剩下 5 项改动，都没覆盖下一个任务里实际遇到的情况，比如清单里列的失败测试和下次碰到的不是同一批。 这 5 项里只有 1 项让对比次数减少，从 5 次降到 2 次，另外 4 项没有变化。 4. 有的改动增加了工作量。 Sphinx 项目的一份失败清单写着"不在清单里的失败，都当成是你自己的修改造成的"。 结果在一个不相关的任务上，5 次里有 4 次 AI 额外做了对比检查（原来是 0 次），用时中位数从 82 秒涨到 245 秒。前面那份有效的 CLAUDE.md 还顺带加了一句"完成前运行格式检查"，AI 每次都照做，用时中位数从 88 秒涨到 156 秒。 至于最后有没有修好问题，用不用这些改动，每组 5 次里的成功次数最多差 1 次，看不出成功率有提高。 作者的结论是，这个项目用什么命令跑测试这类全项目通用的信息，记下来以后一直有用；在某个环境里哪几个测试失败这类信息，换个任务就可能对不上。 评估一项改动，要看问题有没有出现、AI 有没有读这项改动、行为有没有变。保留下来的改动也要持续评估，因为过时或不完整的说明可能不起作用，甚至增加工作量。 作者也说明了研究的局限：每种设置只跑了 5 次，样本小；测试任务是特意挑的会重现问题的任务，可能高估改动的效果；只测了一个 AI 工具、一个版本的 /retro，而且只涉及环境类问题。 论文链接：

Agent 把活干完了，批判性思考还得你自己留住 来自 Claude Code 团队 @addyosmani 的分享，他不主张少用 Agent，而是提醒：模型越好、输出越顺眼，就越没人逼你再想一遍；批判性思考不会自动发生，得自己放进日常习惯 -- 事情可以交给工具来做，对结果负责这件事交不出去。 问题出在哪 以前，很多思考发生在「刚问完」到「答案出来」之间；现在这段空档只剩几秒。并行开很多会话，盯结果的也还是你这一双眼睛。模型变强以后，一眼就能看出的错变少了，多数结果写得像样、大体正确，反而更少触发「再看一眼」。流程又舒服，忙起来最容易松懈。 作者说得很清楚：他喜欢这些工具，写这篇文章不是为了劝人少用，而是帮已经深度用上 Agent 的人，在「什么都能丢出去」的环境里，把独立判断留住。 三种用法：卸载、往后拖、投降 最上是认知卸载：活交给 AI，结果仍归你；他自己整天这么干，也建议别人这么干。中间是把判断往后拖：工具的输出直接变成下一步输入，不再当假设。最下是沃顿学者提出的认知投降：AI 说的悄悄变成你自己的话，也不想再核。 滑坡往往一步步都显得合理：上次认真读了，这次略读，再下次只扫骨架，直到被人问起某一行，连带着 Agent 也说不清。团队里会表现为对共同系统理解越来越薄；代码里则是理解债，测试是绿的、代码看起来干净，真要改系统才发现没人懂。 Claude Code 团队公开说过，他们是用到哪一块就让 Claude 解释哪一块，而不是脑中常驻整仓模型；关键是清楚自己缺哪一块。低风险的事（比如从三家差不多的酒店里选录课场地）可以全权交给 AI；投资、给孩子择业建议，以及工作里做什么产品、改动影响哪些用户、能不能上线，推理还得留在自己手里。错了代价低的可以放手，会影响别人的，推理别交出去。 动手前先问自己几句 他现在常问自己： · 动手之前有没有先立一个哪怕很差的假设（否则读完漂亮回答，就很难再想象别的可能） · 是在请它帮你想，还是替你想 · 怎样才能证明它是错的 · 有没有让别的模型唱反调 · 能不能当着维护者的面为结果担保 · 自己故意不再练哪些技能 没有方向时，也可以先做一次「盲区扫描」：把已知交给模型，让它帮你找不知道自己不知道的地方。 核验要成习惯，别迷信绿灯 核验已经从「写代码」变成瓶颈：给 Agent 端到端测试、属性测试或真机交互，让它改完就测、读结果、再改。但绿灯也可能是假安心，测试和功能犯同一错就会一起过，一个指标也不等于全覆盖。 所以先约定「怎样才算验证过」，先看它跑了什么命令、输出是什么，再看摘要；可以用新开的子代理自检，并习惯问「还漏了什么」。Claude Code 团队有一条经验：说不清这些检查会漏什么，就别急着点批准。客户访谈摘要、竞品分析也一样，抽查原文和关键数字。 真看产出，别只扫结构 面对几百行 PR，别只盯你本来就觉得会出错的地方：把 diff 当人写的来读，再追问 Agent 替你做了哪些默认选择、划了哪些范围、需求冲突时怎么取舍；可以让它列出决策和假设，甚至出个小测，答对再合并。 产出速度快过你敢署名的速度，就是他所说的编排成本，再开一轮会话帮不上，要么把检查收紧，要么放慢。敢署名的量跟不上时，你已经不是在审，而是在赌。 输入和品味仍在两端 人的心力移到两端：前端把任务、受众、范围外、怎样算做完写清楚；后端按自己的标准把关。 人会追问模糊需求，Agent 常会直接补洞，形成意图债，意图只能来自你。提示词写不清楚，往往说明问题在自己脑子里也不清楚；改了两轮还不对，别只微调，重写需求。排版自信不再等于质量，不敢署上自己名字的就不发出去。不达标的原因记进共享配置、钩子或测试，品味才会一点点攒起来。 模型更强，也交不出问责 模型以后也许更会抓错，但「做什么、为什么值得、影响谁、愿意牺牲什么」仍是人的。Anthropic 研究也点过监督悖论：监督 Claude 需要的，正是可能因过度依赖而萎缩的编码能力。 活和大量核验可以卸掉，对结果负责这件事卸不掉。 日常可以怎么做 每周亲手做一件忘了会疼的事；每月盘点停练了什么、哪些可以接受；把认真核验当成正经工作排进时间。停练的技能会掉，而且可能掉得比你想的快。 现在就开始执行起来：有意设置检查；诚实看待自己有没有还在扛结果；先假设；绿灯只证明一件事；先证据后摘要；看清它替你做的决策；提示词反映你对问题的理解；达不到署名标准就不发出。
